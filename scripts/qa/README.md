# Проверка кита в живом браузере

Прогоняет все истории Storybook в Chrome (1280 и 375), снимает скриншоты и
замеряет DOM. Нужен установленный Chrome (путь можно задать `CHROME_PATH`).

```
npm run qa -- build before          # собрать Storybook в .qa/before
npm run qa -- audit before base     # прогон: скриншоты + замеры → .qa/out/before-base
npm run qa -- audit before hard     # то же, но во все текстовые аргументы подставляются
                                    #   длинное слово, "" и 0
npm run qa -- compare before-base after-base    # попиксельная сверка двух прогонов
npm run qa -- drill before <id истории…>        # какой аргумент растягивает страницу на 375
npm run qa -- fuzz before --iterations 25 --seed 3   # случайные сочетания пропсов по argTypes
npm run qa -- scenarios before [--filter текст]      # записанные сценарии взаимодействия
```

## Три слоя

1. **`audit`** — скриншоты и замеры всех историй; `hard` подставляет длинное слово, `""` и 0.
2. **`fuzz`** — случайные сочетания пропсов, каждое сжимается до минимального набора аргументов,
   который воспроизводит сбой. Воспроизводится по `--seed`. Принятые находки лежат в
   `known-findings.json` (подпись → причина) и скрываются; `--all` показывает всё. Новая
   находка — либо ошибка (чиним), либо решение (дописываем в файл с причиной).
3. **`scenarios`** — сценарии в `scripts/qa/scenarios/*.mjs` (маски, попапы, фокус, таблицы):
   проверяют значения, а не классы. Образец — `scenarios/_example.mjs`. Красный сценарий = баг.

Цикл проверки правки: `build before` → `audit before base` → правка →
`build after` → `audit after base` → `compare before-base after-base`.
Два прогона одной сборки дают 0 расхождений, так что любая разница — от правки.

Что ловит замер: переполнение страницы по ширине, элементы за краем окна,
«NaN/undefined/null/[object Object]» в тексте, ошибки консоли и падение истории.
Чего не ловит: вертикальные зазоры, пустые обёртки, наложение соседей и цвета —
для них остаются скриншоты.

Параллельность: не поднимайте `--workers` выше 3, иначе под нагрузкой сценарии падают по таймаутам.

Как читать результат `hard`: сравнивайте с `base` той же сборки. Историю с
демо-обёрткой фиксированной ширины (`w-96`, `w-fit`) даёт ложное срабатывание;
настоящая находка — та, где в обычной колонке текст выходит за край.
Не считать ошибкой в `hard`: `0` в текстовом аргументе, который в типах строка.
